01 Design system

The visual language is genuinely good — a warm parchment ground, obsidian ink, a serif/sans pairing with real character, and a vertical rhythm held consistently across fourteen sections. The system describing it is the problem.

The bronze has forked five ways

src/index.css defines --highlight: 32 33% 65% — the soft bronze that carries every call to action on the site. Nothing references it. Instead the raw hex is pasted into components, and it has already drifted into five values that no one can now tell apart by eye:

The sharpest illustration sits in PensionFeeCalculator.tsx: a component with a prop literally named highlight, which renders border-[#C3AD96]/50 — a hardcoded hex that is not even the token of the same name.

High

141 hardcoded hexes bypass the token layer

D-01

A palette change — including the WCAG contrast fix still outstanding — is a 141-site find-and-replace across five near-identical values, not a one-line token edit. The drift is already here; it will keep widening.

Fix — map the five to their intended roles, expose them as --highlight / --highlight-hover, and add a lint rule banning raw hex outside index.css. That last part is what stops it recurring.

Medium

The home page is a 24-section scroll with three separate AI chats

D-02

Hero, credentials, carriers, about, reviews, perspective, services, needs-interview chat, calculator, quick contact, proof, testimonials, FAQ, booking chat, consultation wizard, detailed form, share, blog-recommender chat, detailed FAQ — then nav, sticky bar, footer.

That is five separate ways to start a conversation, three of them chatbots, competing on one page. Each is individually well built; together they compete for the same decision and dilute it.

Fix — pick one primary conversion path per scroll depth. The three agents plausibly belong behind a single launcher with a mode switch, not as three inline sections.

Sound

Vertical rhythm and the type pairing hold

D-03

Fourteen sections use exactly py-24 md:py-32 — no drift at all. Frank Ruhl Libre against Heebo is a deliberate, well-judged Hebrew pairing, and the eyebrow-label device is applied consistently. The craft is consistent; only the token plumbing is not.

Medium

33 files in one folder with no internal grouping

S-01

Stars.tsx (22 lines, a leaf primitive) sits beside ConsultationBuilder.tsx (350 lines, a multi-step form with backend calls). Nothing in the layout distinguishes a shared primitive from a one-off page section, so reuse is discovered by memory.

Fix — split by role: sections/, forms/, chat/, primitives/. Mechanical, and it makes the next finding visible instead of invisible.

Low

src/lib/ is a catch-all

S-02

It holds the auth context, the query client, the SEO engine, URL helpers, and PageNotFound.jsx — a rendered page living in a utilities folder.

Fix — move PageNotFound to pages/. The rest can stay until the folder grows further.

03 Patterns

The same four or five shapes are re-implemented by hand each time they are needed. Each copy is competent; the cost is that every fix has to be made three or four times, and the copies have already diverged.

High

One submission state machine, four implementations, two vocabularies

P-01

All four forms model the identical idle → sending → sent / error flow. Two call it busy/sent, two call it sending/done. The failure copy is written out three times, differing only in the noun:

  • “לא הצלחנו לשלוח כרגע…”
  • “לא הצלחנו לשלוח את הטופס כרגע…”
  • “לא הצלחנו לשלוח את הבקשה כרגע…”

Each embeds the contact address in the string, even though src/config/contact.js exists precisely to hold it — so the address is duplicated in prose in three files and will be missed by the next change to it.

Fix — one useSubmission() hook owning the state and the error copy, with the address interpolated from CONTACT.email. The four forms keep their own fields and validation.

High

Three chat components, ~30 lines of genuine difference

P-02

NeedsInterviewChat and BookingAssistantChat are both 194 lines; BlogRecommenderChat is 214. Ignoring names, only about 30 lines differ between the first two — the agent name, the greeting, and the section copy. Conversation lifecycle, subscription, scroll handling, send, reset and markdown rendering are triplicated verbatim.

This is why the missing aria-label on the message box was three separate bugs rather than one.

Fix — a single <AgentChat agent="…" greeting="…" />. Roughly 400 lines disappear and future fixes land once.

Medium

Data fetching is hand-rolled in 14 files while React Query sits idle

P-03

@tanstack/react-query is installed, configured with retry and refetchOnWindowFocus, and mounted at the root — and is used by exactly one component, PageNotFound. Everywhere else is useEffect plus manual loading/error state, with no caching, no retry, and no deduplication.

Fix — decide. Move entity reads onto useQuery and inherit retry and caching, or drop the dependency. Two idioms for one job is the only outcome worth avoiding.

Medium

Silent-catch is the house error-handling idiom

P-04

catch (e) { /* מיטבי */ } — “best effort” — appears throughout the backend functions and formerly throughout the components. It is applied to the Lead entity write, which is the durable record of an enquiry. A failure there produces no log, no retry and no signal.

The pattern is reasonable for a calendar hop and wrong for the database write; it is currently used for both.

Fix — keep silent-catch for genuinely optional side effects, and make the record write the operation whose failure is reported. This is the same defect as R-01 in the architecture review.

Low

Email HTML is assembled with raw interpolation

P-05

The confirmation emails build ~90 lines of HTML per function via template literals, interpolating ${firstName}, ${topic} and ${claimTypeLabel} with no escaping anywhere in base44/functions/. The two functions also duplicate the entire shell — header, signature, footer.

Fix — one shared layout helper plus an escapeHtml() for interpolated values.

04 Tests

710 cases pass across four platforms, and they have already earned their keep — seven real defects surfaced from writing them. The honest weakness is that coverage tracks what I wrote tests for, not what the app now does.

High

The three AI agents have no tests at all

T-01

They are the newest, least-proven and most abusable surface in the app: three LLM agents reachable by any anonymous visitor, one of them holding Lead.create plus write access to two real calendars. The suite stubs their transport so other tests stay quiet, and asserts nothing about them.

Fix — cover what is deterministic: the conversation opens, a message posts, a transport failure degrades without breaking the page, and the tool permissions in the agent definitions stay within what each agent needs (a contract test over base44/agents/*.jsonc).

Medium

19 of 33 components are never referenced by a test

T-02

Including Hero, About, ServiceMatrix, Testimonials, CredentialsStrip and the two calendar-booking components. Several are covered incidentally by page-level e2e, but nothing asserts their behaviour.

ClaimForm is the notable gap: its critical labelling bug was caught by a page-level axe scan, not by any test of the form itself, and its submission path has no e2e at all.

Fix — an e2e for the claim submission journey first; it is the highest-stakes form in the app.

Medium

Backend functions are asserted by reading them, not by running them

T-03

The contract suite greps entry.ts for its guard, its status codes and its response shape. That catches drift but proves no behaviour: it cannot tell you that a failed SendEmail loses the lead — which is exactly the live defect in submitLead.

Fix — the functions are plain modules with an injected client. Import and invoke them with a stub to test ordering and failure handling directly.

Sound

The contract tests survived a 44-commit architecture change

T-04

When lead capture moved from the browser to a backend function, the contract suite failed loudly and precisely — pointing at the exact call sites that had moved. Because it reads real source rather than restating payloads, updating it was mechanical. That is the behaviour you want from a contract test.

Worth stating plainly

Coverage counts measure the tests, not the app. 710 green cases sit alongside an untested agent surface with calendar-write access. Weight the next tests by consequence, not by what is easy to reach.

05 Suggested order

Sequenced so each step makes the next cheaper, and the two that can lose a real enquiry come first.
