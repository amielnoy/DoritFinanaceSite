01 What the system is

A marketing, lead-generation and client-service site for an independent Israeli financial planner and insurance agent, in Hebrew with right-to-left layout. The browser app is hosted on Vercel; its data, authentication, files and most server logic live in Supabase; Base44, where the site began, still runs two of the chat agents and a few legacy functions.

The business still comes down to a visitor handing over a name and a phone number, but the paths to it have multiplied: the short contact form, the needs questionnaire, the pension-portfolio check, the claims report, two chat agents, the calculators on /tools and a year-end campaign page. Behind sign-in there is a personal area (the visitor's own enquiries, and — behind a switch — a published personal snapshot), and an admin and staff area: leads, the blog, the clearinghouse requests and their analysis, and the users.

There is still no native app. Mobile is the same SPA at a phone viewport; the e2e suite drives it through the android-chrome device profile.

02 Runtime topology

No longer same-origin. The browser loads the site from Vercel and then talks to Supabase directly — PostgREST under row-level security, Auth, Storage and the Edge Functions — while Base44 is reached through a Vercel rewrite and the agent socket. The Edge Functions, not the browser, hold every secret that reaches beyond the site.

Figure 1 — Request paths Accent: the browser's own calls. Dashed: server to server, secrets held server-side.

What the change bought: Postgres row-level security is now the single gate on every read, and the public site cannot write a lead directly at all — leads has no insert policy for anon or authenticated (20261013010000_no_public_lead_inserts.sql). Every write goes through an Edge Function running as the service role, which is why each of them carries its own validation, rate limit and logging. What it cost: the end-to-end suite now intercepts three origins (Base44, Supabase and analytics) instead of one, and the switches in §4.6 decide which of two stacks a given call reaches.

03 Frontend

Routing

All routes are in src/App.jsx. Home is the only eager page; every other one — and PageNotFound — is React.lazy under one Suspense. Thirteen are public (/, /tools, /pension-check, /claims, /faq, /atzmaim-31-12, /perspective, /blog, /blog/:key, /masleka, /privacy, /accessibility, /login). /account sits in a <ProtectedRoute>. /admin/leads, /admin/blog and /admin/users sit in an <AdminRoute> (role admin in profiles). The three clearinghouse screens sit in a <StaffRoute> — an admin or any agency member, by the my_staff_role() RPC — and are registered only when VITE_MASLEKA_ENABLED is on. Row data is locked down by RLS regardless; the guards keep the pages out of reach.

When VITE_LOCALES names en and fr, six pages are also routed under each prefix (TRANSLATED_ROUTES in src/i18n/locales.ts), inside a LocaleLayout that sets the language and the direction. It is off in production and on in Vercel Preview.

Composition

The home page is now thirteen sections, each in its own <ErrorBoundary>, down from sixteen: the tools moved to /tools, the essay to /perspective, and the five competing contact paths became one start section. Section ids remain the navigation contract — the header, the footer, the sticky bar and CTAs on other pages reach them through useSectionNav, which routes home first, in the visitor's language.

State and data

One idiom now. Ten files use TanStack Query for every server read and mutation; the hand-rolled useEffect fetches are gone. The browser never touches a table or a function by name: it calls the ports in src/services/ports.ts, and src/services/composition.ts picks an adapter per port. src/services/index.ts is a lazy proxy, so the Supabase and Base44 SDKs (vendor chunks of 55 KB and 45 KB gzipped) load only when a call needs them — public article reads go over plain fetch to PostgREST without either.

Languages

Visible text lives in src/i18n/locales/<lang>/<ns>.json — seven namespaces (common, home, pension, faq, claims, yearend, tools) in Hebrew, English and French. Hebrew is the source: its keys are the TypeScript type, so a misspelt key fails the build, and a test holds the other two languages to the same keys and placeholders. Values the site sends stay Hebrew whatever the page's language — a lead's topic and summary, questionnaire answers, claim types, GA4's closed values — with a Hebrew note when the visitor wrote from the English or French site.

Measurement

src/lib/analytics.ts is still the one place that talks to GA4 — one delegated click listener plus explicit events, eighteen of them catalogued in LEAD_EVENTS, with generate_lead sent only after a save succeeds and only closed parameters allowed. Vercel Analytics is added on Vercel builds, with the URL fragment stripped.

Search and sharing

useSeo writes each route's title, description, canonical, social cards, JSON-LD and — for translated pages — hreflang. The build then prerenders the ten public pages (and every published article, and the English and French pages when enabled) so a crawler receives the page, not an empty root. It refuses to ship two routes with one title, or an English or French page with a Hebrew title. api/og/blog.ts answers crawlers for an article published since the last build.

Styling

Tailwind over HSL tokens in src/index.css, and nothing else: an ESLint rule fails the build on a raw hex colour in application code. The bronze that once forked into five near-identical values is now --accent (text, 6.9:1) and --highlight (strokes). The four typefaces are self-hosted (src/fonts.css, font-src 'self'). The two justified exceptions to the hex ban — Google's logo and the organizations' identity colours — carry an explicit comment.

04 Backend

Supabase holds the data and does the work: 19 tables under row-level security, 30 database functions, 6 scheduled jobs, 2 storage buckets and 12 Edge Functions (with 19 shared modules), all in supabase/ and in version control. Migrations are applied by hand, once each, and recorded with supabase migration repair.

4.1 · The data model

Multi-tenant from the schema up, with one tenant today: every business row carries an agency_id, and can_see(agency) — a membership or admin check — is the predicate behind almost every policy. Agency 1 is Dorit's.

4.3 · The shape of a request

The spine from Rev 1.0 carried over intact, and the ordering it insisted on is now in the code that matters most: persist first, and fail loudly only if that fails; everything else is best-effort and reported as a warning. submit-lead inserts the lead, returns 500 if it cannot, and only then mails, appends and books — a failed send can no longer lose an enquiry (R-01). Every request mints a short rid carried through single-line JSON logs; no response carries an underlying error or a token.

Every function has verify_jwt off and checks its caller itself — an admin session, a link token, a cron secret — because a public form has no session to verify. The public ones are rate-limited by allow_submission(), an atomic counter keyed on a hashed identifier; the visitor confirmation is limited per hashed recipient, so a form cannot be turned into a mail relay.

4.5 · What leaves the system

  • Mail, through one relay. Every function calls dorit-mailer, a Cloudflare Pages Function holding the Resend key and the sender identity; Base44 and Supabase each have their own bearer token. It sends one message per recipient and reports partial failure.
  • A Google Sheet, as the operational log, and Google Calendar, through a service account rather than Base44's OAuth connectors. Dorit's Outlook gets an ICS invitation by mail.
  • Anthropic, from the chat function only, under a monthly budget that alerts once.

4.6 · Base44, and the switches between the two stacks

Base44 still hosts four agents, the Lead, Contact, BlogPost and Testimonial entities, and eight functions — of which submitLead, escalateToHuman and logSupportChat are now 34-line forwarders to the Edge Functions, while submitClaim, contentAdmin, createConsultationEvent, upsertContact and adminLead still hold logic. Where a lead goes

A lead is written to leads first; then the operations inboxes and Dorit are mailed, the visitor gets a confirmation, the sheet gets a row, and a meeting gets a calendar event and an ICS invitation. The consent the visitor gives names the operating team, and a contract test fails if the code and that wording disagree.

Known gap

Retention is now automatic for chat transcripts (12 months), clearinghouse codes (9 days), snapshots (24 months) and claim documents (2 months) — and now for leads: anonymized 24 months after the last contact, their sheet rows emptied with them. The mailed copies are Dorit's alone and deleted by hand, as the privacy policy now says. See N-02.

06 The boot path

Rev 1.0's largest finding is closed: nothing stands between a visitor and the page.

Figure 2 — Critical path to first meaningful paint The prerendered HTML is the page; the app takes over without a round trip.

main.jsx installs a Trusted Types policy, leaves the legacy Base44 host if the page was opened there (noindex, canonical to production, redirect), and renders. AuthProvider no longer asks Base44 for public settings before painting: it probes local storage for a session and calls me() only if there is one. A page-level error boundary (keyed on the path) and one per home section fall back to Dorit's phone, WhatsApp and email. A chunk that fails to load after a deploy — an old tab asking for a file that no longer exists — is caught by src/lib/freshness.ts, which reloads once onto the new build.

07 Build & delivery

Every deploy goes through CI; Vercel's Git deploys are off. The build job runs lint, the type check and build:prerender with PRERENDER_REQUIRED=1, and uploads the artifact the e2e shards then test. Production is promoted only from main, only when unit, e2e and the Edge Function deploy have all passed and the Base44 agents have been published — otherwise the same build goes out as a preview with a warning. main itself is protected: the protect-main ruleset requires the Safe to merge? check on every pull request.

High

Enquiries still go first to the developer's personal inboxes

N-01

NOTIFY_EMAILS in supabase/functions/submit-lead/lead.js names two personal addresses as the primary recipients; Dorit's is a secondary copy. The same list is copied by hand into submit-claim and escalate-to-human, and the calendar events go to the operator's own calendar. The consent text discloses the operating team, so this is no longer hidden — but for a regulated adviser the client's details should reach the adviser first, and handing the site over means editing three files and a secret.

Fix — one recipients module in _shared/, Dorit primary, the operating team as a disclosed copy; a function secret for the list. The contract test that pins the consent wording follows the change.

Status · #224 — the three copies are one module, supabase/functions/_shared/recipients.ts, with the diary derived from it and an optional NOTIFY_EMAILS secret. Who receives is unchanged by decision (the user, 15 October): the operating team and Dorit, as the consent discloses. Changing it is now one line, or the secret.

High

Leads are never deleted

N-02

The privacy policy promises deletion after 24 months. Every other kind of personal data now has a purge job; leads, contacts and meetings do not, and nor do the sheet rows or the mailed copies — which is what a deletion request under Amendment 13 asks about.

Fix — a delete_after column and a nightly purge like the chat's, with the sheet row cleared by the same job; and say in the policy what happens to mailed copies.

Status · fixed in #223 (migration applied 15 October) — a client status, set in /admin/leads, exempts an engagement; every other lead is anonymized nightly at 03:45, 24 months after its last contact, keeping date, source, topic and status; old contact records go with it. The sheet follows nightly at 04:30 (sheet-retention): an anonymized or deleted lead's row loses its personal cells, an unlinked row after 24 months, a Support row's phone and transcript after 12 (#230). The mailed copies (#231): the operating team now gets a notice without the visitor's details, and its diary a meeting's name, phone and topic; only Dorit receives the enquiry, and the privacy policy (§7) says those copies are deleted at the end of the same period — by hand, the one part code cannot reach.

Medium

Two backends, chosen by switches whose defaults are the old one

N-03

Production runs Supabase for leads, uploads, the clearinghouse and two agents, but content writes still go through Base44's contentAdmin, two agents still run there, and every switch defaults to Base44. submitClaim exists twice (Base44, 630 lines; Edge, 260). Each Base44 path is a second implementation to keep in step, and the e2e suite tests the defaults rather than what production runs.

Fix — finish the exit: set VITE_CONTENT_WRITES=supabase, move the last two agents to the chat function, revoke the Base44 connectors, then flip the defaults and delete the dead paths.

Medium

The remaining Base44 functions are never type-checked

N-04

CI runs deno check on the Edge Functions, but nothing checks base44/functions/, where submitClaim, createConsultationEvent, upsertContact and contentAdmin still hold real logic. Rev 1.0's "Unchecked" callout still applies to them.

Fix — retiring them (N-03) is the real fix; until then, a deno check step over base44/functions/*/entry.ts.

Status — tried on 15 October: the step cannot resolve npm:@base44/sdk outside Base44, and past that reports dozens of implicit-any errors in code due for retirement. Left to N-03.

Medium

Production depends on manual steps CI cannot see

N-05

Migrations are applied by hand, and the environment switches are set by hand; the code can reach production ahead of the schema or the switch it needs. #218 is the example from the other direction: a Vercel function broke in production while every local gate was green.

Fix — a CI check that compares supabase migration list against the repository before promoting, and a smoke step that probes each function (now done for /api/og/blog by hand).

Status · fixed — the smoke job now probes both Vercel functions after every production deploy (a 404 and a 405 that only a loaded function returns). The migration-drift check is built (#226, #228): before the functions deploy, CI reads production's history from the Management API and stops on a migration the repository has and production does not. It reads with its own token, SUPABASE_MIGRATIONS_TOKEN (only database_migrations_read, set 15 October), and on main answered "All 25 migrations in the repository are applied in production." A history it cannot read still warns rather than blocks.

N-06 · N-07 · N-08

N-06 — the main chunk is 489 KB (146 KB gzipped) because Home and its sections are eager by design; worth a measurement before a change, since Home is the page that must paint first.

Sound

What the architecture gets right

N-09

The public cannot write a table; every write is a function with its own guard and rate limit, and every read is an RLS policy with a SQL test behind it. Sealed clearinghouse codes are revealed one value at a time, audit-logged first, and wiped on a schedule. Nothing blocks first paint, and an error anywhere still leaves Dorit's phone number on the screen. New features ship dark behind switches, and the Hebrew site is held unchanged by rendered-text comparisons when they land. Raw colours fail the lint, a missing translation fails the build, a Hebrew title on an English page fails the prerender.
