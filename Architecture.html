01 What the system is

A single-page marketing and lead-generation site for an independent Israeli insurance and financial adviser, in Hebrew with right-to-left layout, running on the Base44 platform.

Everything the business needs from it comes down to three transactions: a visitor reads the adviser's story and services, a visitor models what their pension management fees actually cost them, and a visitor hands over a name and a phone number. A small admin area behind authentication lets the adviser read those leads and publish blog posts.

There is no native mobile application. Mobile is the same SPA at a phone viewport, which is why the test suite's ios-safari and android-chrome platforms drive mobile web through WebKit and Chromium device profiles rather than a device farm.

02 Runtime topology

Everything is same-origin. The SPA never talks to a third party for data — the Base44 edge fronts the entity store, the Core integrations and the function runtime under one /api prefix, which is also why the whole backend can be stubbed at a single route pattern in the tests.

Figure 1 — Request paths Solid: same-origin. Dashed: server-to-server, token from the connector.

The consequence worth naming: because serverUrl is empty in src/api/base44Client.js, every call is relative. That is good for cookies and CORS, and it is what lets the end-to-end suite intercept **/api/** once and run the entire site offline with no credentials and no risk to production data.

03 Frontend

Routing

All thirteen routes are declared in src/App.jsx. Eleven are public; /admin/leads and /admin/blog sit inside an <AdminRoute>, which delegates to <ProtectedRoute> when the visitor is signed out — redirecting to /login — and additionally sends anyone whose role is not admin back to the home page. The row data is already locked down by RLS; the gate keeps the page itself out of reach. Every page module is imported eagerly at the top of the file, so the router does no code splitting — see finding R-05.

Composition

The home page is a single scroll of sixteen sections, each an independent component in src/components/dorit/ with its own anchor id. Section ids are the site's real navigation contract: the header nav, the section rail, the mobile sticky bar and the calculator's call-to-action all target them, and the test suite asserts all twelve top-level ids exist.

State and data

There are two idioms in the codebase and only one of them is used. @tanstack/react-query is installed, configured in src/lib/query-client.js and mounted in App.jsx — but the only useQuery call in the whole application is in PageNotFound.jsx. Every other fetch is a hand-rolled useEffect with local loading / error state. Authentication state is a plain React context.

Why it matters

Two idioms means two sets of caching, retry and error semantics for the same backend, and the one that is actually used is the one with none. Reviewers have to read each component to know how it fails.

Styling

Tailwind utilities over HSL custom properties declared in src/index.css — --background, --foreground, --accent and friends. Two brand colours are also hard-coded as hex literals throughout the dorit/ components (#C4A484 and #7D6B5D) rather than going through the token layer, which is what makes the contrast finding in R-09 a multi-file change instead of a one-token change.

04 Backend

Declarative, and unusually well-scoped. The backend is four JSON entity definitions, two Core integrations and one Deno function — all in base44/, all in version control.

The Lead rules are exactly right for the job: anyone may submit, only an admin may read. That single line is what stands between a public contact form and a public list of clients' names and phone numbers, which is why the contract suite asserts it explicitly rather than trusting it.

The one function

createConsultationEvent takes a booking, pulls a Google access token from the googlecalendar connector under asServiceRole, and writes a follow-up event for 09:00 Jerusalem time the next day. It validates name and phone, returns 400 without them, 502 when Google refuses, 500 on anything else, and never puts the access token in a response. Its request shape and every one of those status codes are pinned by contract tests.

05 The boot path

This is the architectural decision with the largest business consequence, so it gets its own figure.

AuthProvider calls base44.app.getPublicSettings() on mount, and AuthenticatedApp renders a spinner — nothing else — until that promise resolves. Every route sits behind it, including the entirely public marketing pages. If the call returns a 403 with auth_required, the visitor is redirected to a login screen.

Figure 2 — Critical path to first meaningful paint The marketing content cannot paint until an API round trip that has nothing to do with it resolves.

For an authenticated product this design is correct. For a lead generation site it inverts the priority: the content that earns the phone call is gated on a service that only the admin area needs. The project's own README documents the sharp edge — before the app has been published once, that call fails and every page redirects to login.

06 Build & delivery

vite build emits one JavaScript chunk and one stylesheet into dist/. Delivery is git-based: pushing to main syncs the repository to Base44, and the app is published from the Base44 dashboard. A CLI base44 deploy ships the local tree directly and bypasses that sync, so the deployed state silently diverges from the repository — which is why the CI workflow treats publishing as an opt-in step gated on credentials rather than something that happens on every green build.

The Builder writes directly to the trunk, without review and without tests — twice in one day that put a broken suite on main. Nothing reaches the client's site regardless, since the Base44 publish demands a green run, but main itself is not protected from it.

The promote job closes that hole and is dormant: it triggers only on pushes to a builder branch, and pointing the Builder at one is a Base44-side setting that costs Builder tokens. Once switched, every Builder push runs the full battery and reaches main only when all of it is green — fast-forwarding where it can, so what deploys is byte for byte what was tested, and merging where a pull request has landed in the meantime, with main re-testing the combined tree before anything deploys.

There are two deployment targets, and they are gated differently on purpose. Vercel carries staging: it deploys whenever the build succeeds, whether the tests passed or not, because a failing run is precisely when it helps to open the broken build next to the Allure report that says what broke. The site sits behind Vercel Authentication, so a red build is never reachable by the public. Base44 carries production, and its publish job requires every suite to have passed — the strictest gate in the pipeline. A test failure therefore costs the team its staging convenience, never the client's live site.

07 Test architecture

Four layers, two runners, four browser platforms. The full battery runs from one command and inside one pinned container.

The end-to-end layer runs against the production build served by vite preview, so a green run also proves the bundle boots. The whole Base44 surface plus analytics, fonts and media hosts are intercepted in one fixture, which makes the suite hermetic: no credentials, no network, no possibility of writing to production. An opt-in block re-checks the same contract against a real backend when one is available.

Test-first payoff

Five defects were found by writing these tests, not by reading the code: a broken manifest.json reference masked by the SPA fallback, a 38-pixel mobile tap target, two screen-reader defects on the star ratings and the proof carousel, and a console-error source that only reproduced inside the container.

08 Review findings

Ordered by business consequence, not by how interesting they are to fix. Each references the test that would catch a regression once addressed.

High

Lead capture treats the durable record as optional

R-01

All three forms do the same thing in the same order: send an email, and then try to write the Lead entity inside a try whose catch is empty. If SendEmail fails, the visitor sees an error and the lead is never persisted at all. If Lead.create fails, nobody finds out — the visitor is thanked and the enquiry evaporates.

The email is the fragile channel (deliverability, verified domains, registered recipients) and it is load-bearing; the database write is the reliable one and it is best-effort.

Fix — invert the order: persist the Lead first and treat that as success, then notify. Surface a failure only when the persist fails. Covered today by E2E-FRM-002/003/004, which will pin the new ordering.

High

Client enquiries are addressed to a developer's personal inbox

R-02

NOTIFY_EMAIL = "amielnoy@gmail.com" is hard-coded in QuickContact.tsx, DetailedContactForm.tsx and ConsultationBuilder.tsx. It is the primary recipient; the adviser's own address is sent as a secondary copy inside a swallowed catch.

The payload is a named individual's phone number, email and the financial matter they want help with. For a regulated adviser that routing is a data-protection question, not a configuration detail.

Fix — move both recipients into src/config/contact.js (which already exists for exactly this reason) and make the adviser's address primary. CTR-EML-002 already forbids inline recipient literals.

High

Public content is gated behind an authentication round trip

R-03

Described in full in §5. First paint of a marketing page depends on getPublicSettings(); a failure sends the visitor to a login screen on a site that has nothing to log into.

Fix — render public routes immediately and resolve auth in the background; keep the gate on <ProtectedRoute>, where it belongs. E2E-HOM-001 and E2E-HOM-006 already assert the page survives a dead backend.

Medium

No error boundary anywhere in the tree

R-04

A render-time throw in any one of the sixteen home-page sections unmounts the entire application and leaves a white screen — no phone number, no WhatsApp link, no fallback.

Fix — one boundary around <Routes> and one per home-page section, falling back to the contact details. SEC-ERR-001 watches for uncaught errors but cannot recover from them.

Medium

One 790 KB chunk, and roughly a dozen dependencies nothing imports

R-05

Every route is imported eagerly, so a visitor reading the privacy policy downloads the blog admin, the rich-text editor and the calculator. Vite's own build warns about the chunk size.

Separately, three, jspdf, html2canvas, moment, lodash, react-leaflet, @stripe/react-stripe-js, react-quill-new, @hello-pangea/dnd and canvas-confetti are declared dependencies with no import anywhere in src/ — starter-template residue.

Fix — React.lazy for the admin routes and the blog first (they are never on the marketing critical path), then prune the unused packages. API-HTP-009 keeps asserting that every emitted asset resolves.

Medium

The same 40 lines of lead submission live in three components

R-06

Recipient constants, message body assembly, email send, secondary copy, entity write and error copy are duplicated across QuickContact, DetailedContactForm and ConsultationBuilder. R-01 and R-02 each have to be fixed three times because of it.

Fix — one submitLead(payload, source) in src/lib/; the components keep their own field validation and copy. The contract suite reads the real call sites, so it follows the refactor automatically.

Medium

React Query is mounted but effectively unused

R-07

The provider, the client and the default options are all configured; one component uses it. Everything else re-implements loading and error state by hand, with no caching and no retry.

Fix — pick one. Either move the entity reads onto useQuery and get retry and caching for free, or drop the dependency. Two idioms is the only outcome worth avoiding.

Medium

npm run typecheck fails on main

R-08

Roughly 74 errors, all pre-existing: components passing props to untyped shadcn wrappers (Image, the accordion primitives) plus one lucide icon prop-variance mismatch. Nothing breaks at runtime because Vite strips types without checking them — which is exactly why the errors have been able to accumulate.

Fix — type src/components/ui/image.jsx and the accordion wrapper, then make the check blocking in scripts/run-tests.sh and CI. Both currently carry a comment pointing at this finding.

Medium

Brand accent falls just short of WCAG AA contrast

R-09

#7D6B5D on #F9F7F2 measures about 4.4:1 against a 4.5:1 floor — 41 elements on the home page, mostly 11-pixel uppercase eyebrow labels, plus the footer greys on every page. The site publishes an accessibility statement, so this is a stated commitment it currently misses.

Fix — darken --accent to roughly 26 14% 34%, or lift the small labels to --foreground. The a11y suite reports it on every run and enforces it under E2E_ENFORCE_CONTRAST=1.

Low

Three smaller items

R-10 · R-11 · R-12

R-10 — the JSON-LD in index.html publishes dorit@govari-fin.co.il while every visible surface uses doritg@fsfp-fin.co.il. Search engines and AI crawlers read the former. Left unchanged because which address is canonical is a business fact, not a code decision.

R-11 — src/lib/utils.js reads window at module scope, so the module cannot load outside a browser. It forces its own unit tests into jsdom and would block any future prerender step.

R-12 — the Deno function pins @base44/sdk@0.8.44 while the frontend tracks ^0.8.48. Harmless today, a silent drift generator later.

Sound

What the architecture already gets right

R-13

Entity row-level security is scoped correctly and deliberately — the lead inbox is admin-read, and no entity is world-writable. The ?returnTo= open-redirect guard is centralised in one documented module and handles the non-obvious /.//evil.com and backslash cases. Blog markdown renders without rehype-raw, closing the stored-XSS hole. The Deno function takes its token from the connector and never echoes it. Contact details already live in one config module. All of it is now pinned by tests.
