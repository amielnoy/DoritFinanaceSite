## 3. מה נאסר על הסוכנים — ומה קורה במקום זה

כל אחד מאלה מסתיים בהעברה לאדם, ולא בתשובה חלקית:

| הבקשה | הסיבה המדווחת |
|---|---|
| המלצה על מוצר, מסלול או גוף מוסדי; השוואה ביניהם | `product_recommendation` |
| תשואות, דמי ניהול, סכומים, חישוב או חבות מס | `numbers_or_returns` |
| כדאיות ניוד, משיכה, קיבוע זכויות, תיקון 190, ביטול פוליסה | `regulated_advice` |
| פרשנות פוליסה, זכאות לתביעה, סיכויי תביעה | `claim_or_policy` |
| תלונה, טענה לנזק, איום בהליך | `complaint` |
| בקשת עיון, תיקון, מחיקה או ביטול הסכמה | `privacy_request` |
| מבקר שמסר מיוזמתו ת״ז, מספרי חשבון, נתוני שכר או מידע רפואי | `sensitive_data` |
| נושא מחוץ לתחום הסוכן | `out_of_scope` |
| בקשה מפורשת לדבר עם אדם | `user_request` |
| **כל מצב שבו הסוכן אינו בטוח שמותר לו לענות** | `uncertain` |

השורה האחרונה היא הכלל שמחזיק את כל השאר: ספק פועל לטובת ההעברה, והסוכן אינו
רשאי לנחש.

## 5. מסלול ההעברה לאדם

1. הסוכן קורא ל-`escalateToHuman` עם `reason`, `summary` ופרטי הקשר אם נמסרו.
2. הפונקציה מסננת מזהים רגישים מהתקציר.
3. אם נמסרו שם וטלפון תקינים — נוצרת רשומת `Lead` עם `source='escalation'`,
   `status='escalated'` ו-`escalation_reason`.
4. נשלחת התראה לדורית בכל מקרה — גם כשאין פרטים לשמור. פנייה שהועברה ולא
   הגיעה לאדם היא כשל רגולטורי, ולכן ההתראה אינה מותנית בשמירה.
5. הסוכן מוסר למבקר את `contact` ואת `acknowledgement` שחזרו.
6. בכשל מלא — הסוכן מוסר את הטלפון והמייל הקבועים.
